\chapter{Metodología técnica y de desarrollo}\label{cap:metodologia_tecnica}

Una vez establecida la arquitectura y el diseño conceptual del sistema, resulta imprescindible definir un marco operativo riguroso para la fase de construcción e integración del código. En el desarrollo de software, la ausencia de políticas explícitas en el control de versiones incrementa paulatinamente la deuda técnica y dificulta la detección temprana de errores.

Este capítulo detalla la metodología técnica implantada en el proyecto \textit{Quizzie}. En él se abordan las políticas de trabajo en el repositorio, la automatización del ciclo de Integración y Despliegue Continuos (CI/CD), la gestión segura de perfiles de configuración y el análisis estático de la calidad del código.

\section{Ecosistema base de desarrollo local}\label{sec:ecosistema_base}

Concretando la selección tecnológica descrita en la subsección \hyperref[subsec:soporte_desarrollo]{soporte de desarrollo}, el trabajo local se sostiene sobre tres pilares operativos principales. La integración de este ecosistema busca asegurar la reproducibilidad homogénea del proyecto, garantizar el aislamiento de dependencias y simplificar la ejecución de herramientas de desarrollo:

\begin{itemize}
    \item Gestión de entorno \textbf{\textit{backend}} con \textbf{uv}: En lugar de recurrir a entornos virtuales creados manualmente (\texttt{venv}) o gestores tradicionales, el ciclo de vida del \textit{backend} se articula íntegramente mediante el gestor de dependencias \textit{uv}. Esta herramienta centraliza el aislamiento de la versión de Python, la resolución del árbol de dependencias expresado en \texttt{pyproject.toml} y la ejecución de comandos de soporte (linters, formateadores y motores de prueba) en un entorno reproducible mediante el prefijo \texttt{uv run}.
    \item Gestión de entorno \textbf{\textit{frontend}} con \textbf{npm} y \textbf{Node.js}: Para la parte cliente, el ecosistema de trabajo se apoya en \textbf{npm} sobre el entorno de ejecución de \textbf{Node.js}. A través del fichero \texttt{package.json}, se estandarizan las tareas de desarrollo, la compilación y la verificación de tipos con TypeScript.
    \item Sistema de control de versiones distribuido con \textbf{Git}: Registra la evolución del código fuente, sirviendo de nexo entre el trabajo en la máquina local y las políticas de integración remota que se detallan a continuación.
\end{itemize}

Esta combinación permite que cualquier desarrollador pueda clonar el repositorio y levantar el entorno completo de trabajo de forma idéntica con un conjunto mínimo y estandarizado de comandos.

Los pasos detallados para la preparación inicial del entorno y el registro de dependencias se recogen en el \hyperref[anexo:manual_de_instalacion]{manual de instalación}.

\subsection{Gestión de tareas mediante plantillas de \textit{GitHub Issues}}

Todo trabajo de desarrollo, refactorización, documentación o pruebas debe originarse mediante una incidencia (\textit{Issue}) en GitHub. Esto garantiza la trazabilidad bidireccional entre los requisitos funcionales (RF), los objetivos del proyecto y las modificaciones del código.

Para homogeneizar el registro de \textit{Issues}, se han implementado plantillas declarativas en formato \textit{YAML} ubicadas en el directorio \texttt{.github/ISSUE\_TEMPLATE} del repositorio:

\newpage

\begin{itemize}
    \item \texttt{feature\_request.yml}: Diseñada para la implementación de nuevos Requisitos Funcionales. Exige vincular explícitamente el identificador del requisito (ej. \texttt{RF-07}), el objetivo asociado (\texttt{OBJ-02}), la descripción técnica de la solución y los criterios de aceptación.
    \item \texttt{docs.yml}: Orientada a la redacción de documentación técnica o capítulos de la memoria en \LaTeX{}, indicando el documento afectado y los criterios de revisión.
    \item \texttt{devops.yml}: Destinada a tareas de automatización, ajuste de canalizaciones de GitHub Actions, integración con SonarCloud o configuración de infraestructura.
    \item \texttt{test.yml}: Específica para la creación o ampliación de baterías de pruebas (unitarias, integración, de componentes, E2E, o pruebas de carga con Locust).
\end{itemize}

El uso de esta estructura estandarizada asegura que cualquier incidencia registrada contenga los datos necesarios para que el desarrollo posterior se adecúe a los \hyperref[sub:criterios_de_aceptacion]{criterios de aceptación}.

\subsection{Verificación local mediante \textit{pre-commit}}\label{subsec:precommits}

Antes de que cualquier \textit{commit} (modificación en el código) sea registrada definitivamente en el historial de Git, es fundamental asegurar que cumple con los estándares de calidad y formato fijados en el proyecto. Para automatizar este control, en la máquina local del desarrollador se utiliza la herramienta \textbf{pre-commit}, la cual evalúa el código de forma previa a la confirmación.

La configuración centralizada de estas verificaciones se define en el archivo \texttt{.pre-commit-config.yaml} ubicado en la raíz del repositorio. En dicho fichero se declaran los conectores (\textit{hooks}) y herramientas que se deben ejecutar de forma transparente sobre los archivos modificados:

\begin{enumerate}
    \item \textbf{\textit{Backend} (Python):} Se integra la herramienta \textbf{Ruff} para realizar un análisis estático ultra rápido, corregir automáticamente fallos de formato, eliminar importaciones sin usar y garantizar el cumplimiento del estándar PEP 8 \cite{pep8}.
    \item \textbf{\textit{Frontend} (React / TypeScript):} Se ejecutan \textbf{ESLint} y \textbf{Prettier} para inspeccionar la sintaxis de los componentes JSX/TSX y unificar el estilo visual del código.
    \item \textbf{Seguridad y limpieza:} Se añaden verificaciones generales para detectar y bloquear la subida accidental de archivos de secretos (\texttt{.env}), claves privadas o archivos con formato incorrecto.
\end{enumerate}

Para forzar manualmente la inspección de la totalidad del código fuente sin necesidad de intentar un \textit{commit}, se utiliza la instrucción:

\begin{verbatim}
uv run pre-commit run --all-files
\end{verbatim}

Si alguna de las comprobaciones detecta un fallo o una discrepancia de formato, pre-commit aborta la confirmación automáticamente, exigiendo corregir el problema antes de continuar.

\subsection{Estandarización de commits}\label{subsec:estandarizacion_commits}

Para mantener un historial de control de versiones limpio, semántico y legible, se ha adoptado la especificación \textbf{Conventional Commits}. Esta convención asigna un significado explícito a cada confirmación, lo que permite auditar la evolución del código y automatizar la gestión de versiones mediante Versionado Semántico (\textit{SemVer}) \cite{semver}.

La construcción de los mensajes en la máquina local se canaliza a través de la herramienta \textbf{Commitizen}. Al ejecutar la instrucción interactiva correspondiente, se guía al desarrollador en la redacción del mensaje respetando la estructura obligatoria:
\[
\text{\texttt{<tipo>}}(\text{\texttt{<alcance>}}): \text{\texttt{<descripción>}}
\]

\begin{table}[H]
\centering
\small
\makebox[\textwidth][c]{%
\begin{tabular}{l l l}
\hline
\textbf{Tipo} & \textbf{Descripción} & \textbf{Impacto SemVer} \\
\hline
\texttt{feat} & Incorporación de una nueva funcionalidad o requisito. & MINOR (v0.X.0) \\
\texttt{fix} & Corrección de un fallo o error en el código. & PATCH (v0.0.X) \\
\texttt{docs} & Cambios exclusivamente en la documentación o memoria. & Ninguno \\
\texttt{style} & Ajustes de formato o estilo que no alteran la lógica. & Ninguno \\
\texttt{refactor} & Reestructuración de código sin cambio de comportamiento. & Ninguno \\
\texttt{test} & Añadido o corrección de baterías de pruebas. & Ninguno \\
\texttt{build} & Modificaciones en la configuración de build o dependencias. & Ninguno \\
\texttt{ci} & Ajustes en los flujos de integración continua (CI/CD). & Ninguno \\
\hline
\end{tabular}%
}
\caption{Tipos de \textit{commits} según Conventional Commits.}
\label{tab:tipos_commits}
\end{table}

Asimismo, se exige establecer la trazabilidad bidireccional entre el código registrado y las incidencias de GitHub. Para ello, en el pie del mensaje de confirmación se deben incluir las referencias correspondientes:

\begin{itemize}
    \item \texttt{Refs \#83}: Vincula la confirmación con la incidencia \#83 en la interfaz de GitHub para facilitar su seguimiento.
    \item \texttt{Closes \#83} / \texttt{Fixes \#83}: Asocia el cambio y provoca el cierre automático de la incidencia al fusionar la rama en la rama principal (\texttt{main}).
\end{itemize}

Para automatizar este proceso, se ha configurado previamente una plantilla en el proyecto que guía al desarrollador paso a paso. Al ejecutar la siguiente instrucción en la terminal, se despliega el asistente de Commitizen y se genera el \textit{commit} de forma directa en el repositorio local una vez rellenados los campos:

\begin{verbatim}
uv run cz commit
\end{verbatim}

\section{Integración y Despliegue Continuo (CI/CD)}

Para garantizar la calidad del software, la detección temprana de errores, la seguridad de las dependencias y la entrega continua del servicio en \textit{Quizzie}, se ha diseñado e implementado una arquitectura de Integración y Despliegue Continuos (CI/CD) fundamentada en GitHub Actions. Este flujo automatizado actúa como un control de calidad estricto antes de actualizar cualquier versión del código hacia los entornos de integración y producción.

\subsection{Ciclo de vida y arquitectura}\label{subsec:cicd_arquitectura}

El flujo de trabajo automatizado se estructura en tres \textit{workflows} independientes en GitHub Actions, los cuales responden a eventos específicos en el repositorio y gestionan las distintas fases de validación técnica:

\newpage

\begin{enumerate}
    \item \textbf{Integración Continua (CI):} Se activa automáticamente ante eventos de \textit{push} en la rama \texttt{develop}. Ejecuta la batería de análisis estático, seguridad, pruebas unitarias y de integración, de componentes, \textit{End-to-End} y evaluación de rendimiento.
    \item \textbf{Análisis de calidad (QA):} Se dispara tras consolidar cambios en la rama \texttt{main}. Evalúa métricas avanzadas de mantenibilidad, duplicación de código y deuda técnica en la plataforma SonarCloud.
    \item \textbf{Despliegue Continuo (CD):} Se ejecuta de forma paralela al análisis de calidad tras una fusión exitosa en \texttt{main}, activando el despliegue automático en la infraestructura de producción.
\end{enumerate}

\subsection{Flujo de Integración Continua (CI)}\label{subsec:pipeline_ci}

El proceso de validación de calidad y seguridad definido en \texttt{quality\_and\_security.yml} se compone de seis \textit{jobs} interconectados distribuidos en distintas etapas secuenciales:

\subsubsection{Análisis estático y verificación}
\begin{itemize}
    \item \texttt{backend-ci}: Inicializa el entorno Python 3.12 con \texttt{uv}, analiza el formato y estilo del código mediante \textbf{Ruff} y realiza la auditoría de seguridad de dependencias con \texttt{pip-audit}.
    \item \texttt{frontend-ci}: Prepara el entorno Node.js 20, ejecuta la verificación sintáctica mediante \textbf{ESLint} y valida el tipado de TypeScript junto con la compilación del proyecto.
\end{itemize}

\subsubsection{Pruebas de código y componentes}
\begin{itemize}
    \item \texttt{pytest-backend-tests}: Requiere la superación previa de \texttt{backend-ci}. Ejecuta la suite de pruebas unitarias y de integración del \textit{backend} mediante \textbf{Pytest} y exporta el informe de cobertura XML (\texttt{backend-coverage}) como artefacto.
    \item \texttt{vitest-component-tests}: Se ejecuta tras la consecución de \texttt{frontend-ci}. Realiza las pruebas sobre la interfaz de usuario utilizando \textbf{Vitest} y almacena su reporte de cobertura.
\end{itemize}

\subsubsection{Pruebas de sistema y rendimiento}
\begin{itemize}
    \item \texttt{playwright-e2e-tests}: Depende del éxito conjunto de \texttt{pytest-backend-tests} y \texttt{frontend-ci}. Despliega el servidor backend de pruebas y ejecuta la batería \textit{End-to-End} con \textbf{Playwright} simulando la navegación de usuario en navegadores \textit{headless}.
    \item \texttt{locust-performance-tests}: Se inicia tras la superación de \texttt{pytest-backend-tests}. Inicia el servidor de prueba y ejecuta la simulación de carga concurrente con \textbf{Locust}, validando mediante \texttt{evaluate\_thresholds.py} que las latencias y tasas de error se mantengan dentro de los límites establecidos en la \hyperref[sec:estrategia_testing]{estrategia de \textit{testing}}.
\end{itemize}

\subsection{Análisis de calidad con SonarQube}\label{subsec:sonarqube_ci}

Al consolidar cambios en la rama (\texttt{main}), se activa el \textit{workflow} \texttt{sonar.yml}. Este proceso reejecuta la medición de cobertura del \textit{backend} y envía los resultados a la plataforma SonarCloud mediante la acción oficial \texttt{SonarSource/sonarqube-scan-action}, evaluando los umbrales de calidad (\textit{Quality Gate}) y la deuda técnica acumulada.

\subsection{Estrategia de Despliegue Continuo (CD)}\label{subsec:estrategia_cd}

Tras producirse un \textit{push} en la rama \texttt{main}, el despliegue del entorno de producción se efectúa automáticamente de forma segregada:

\begin{itemize}
    \item \textbf{Backend (Render):} Se gestiona mediante el \textit{workflow} \texttt{deploy.yml}, el cual notifica al servicio de Render tras cada \textit{push} en \texttt{main} para activar la actualización del servidor de aplicaciones.
    \item \textbf{Frontend (Vercel):} Se apoya en la integración nativa de Vercel con el repositorio de GitHub, la cual detecta los nuevos \textit{commits} en la rama \texttt{main} e inicia automáticamente la compilación y publicación de la interfaz.
\end{itemize}

\section{Gestión de configuración y entorno}\label{sec:env_secrets}

Para garantizar la seguridad, el cumplimiento de buenas prácticas y la portabilidad entre el desarrollo local y los entornos de producción, \textit{Quizzie} desvincula completamente la configuración del código fuente. Los datos sensibles, credenciales de correo y claves de cifrado se gestionan de forma centralizada mediante variables de entorno seguras.

\subsection{Categorización funcional de los secretos}\label{subsec:categorizacion_secretos}

Las variables de entorno del sistema se estructuran en cinco categorías funcionales según su cometido dentro de la arquitectura:

\begin{itemize}
    \item \textbf{Autenticación y seguridad JWT:} Comprende la clave secreta de firma \textbf{\texttt{SECRET\_KEY}}, el algoritmo de cifrado \textbf{\texttt{ALGORITHM}} y el tiempo de expiración de las sesiones \textbf{\texttt{ACCESS\_TOKEN\_EXPIRE\_MINUTES}}. Garantizan la integridad y validez de los tokens de usuario.
    \item \textbf{Servicio de inteligencia artificial (Gemini API):} Agrupa las credenciales necesarias \textbf{\texttt{GEMINI\_API\_KEY}} para la autenticación y consumo de los modelos de lenguaje de Google Gemini dedicados a la generación automatizada de preguntas y cuestionarios.
    \item \textbf{Servicio de correo transaccional (SMTP):} Incluye los parámetros de conexión al servidor SMTP \textbf{\texttt{SMTP\_HOST}}, \textbf{\texttt{SMTP\_PORT}}, las credenciales de autenticación \textbf{\texttt{SMTP\_USERNAME}}, \textbf{\texttt{SMTP\_PASSWORD}} y la dirección del remitente \textbf{\texttt{SMTP\_FROM}}.
    \item \textbf{Conectividad y cliente React:} Contiene la URL base del backend \textbf{\texttt{VITE\_API\_URL}}, requerida para orientar las peticiones HTTP del frontend tanto en desarrollo local como en producción.
    \item \textbf{Integración continua y calidad (CI/CD):} Agrupa los tokens de autenticación para servicios externos del pipeline, como el token de análisis en SonarCloud \textbf{\texttt{SONAR\_TOKEN}} y la URL del disparador de despliegue en Render \textbf{\texttt{RENDER\_DEPLOY\_HOOK\_URL}}.
\end{itemize}

\subsection{Entorno de desarrollo local}\label{subsec:env_local}

Para facilitar la configuración durante el desarrollo sin comprometer la seguridad del repositorio, se proporciona la plantilla \texttt{.env.example}. Este archivo define la estructura y variables obligatorias del sistema definidas anteriormente.

A partir de dicha plantilla, el desarrollador genera su archivo local \texttt{.env}, ignorado por Git mediante \texttt{.gitignore} para evitar filtraciones. Este proceso se aborda en el \hyperref[anexo:manual_de_instalacion]{manual de instalación}.

\subsection{Distribución de secretos por plataforma}\label{subsec:secretos_plataformas}

Bajo este criterio, se garantiza que cada plataforma o servicio contenga de forma aislada únicamente las variables estrictamente necesarias para cumplir su función técnica, reduciendo la superficie de ataque y minimizando el impacto ante eventuales vulnerabilidades.

\subsubsection{Justificación por entorno}
\begin{itemize}
    \item \textbf{GitHub (Actions):} Registra únicamente las credenciales requeridas para ejecutar las suites de prueba durante los \textit{workflows}, la autenticación del escáner en SonarCloud y el disparador del despliegue en producción.
    \item \textbf{Render (Backend):} Concentra la configuración del servidor de aplicaciones, alojando la infraestructura de correo SMTP, la clave de acceso a la API de Gemini, los parámetros de runtime de Python y la gestión del ciclo de vida de los tokens JWT.
    \item \textbf{Vercel (Frontend):} Contiene exclusivamente el parámetro público \texttt{VITE\_API\_URL} para el enrutamiento de peticiones HTTP desde la SPA React hacia la API, además de los parámetros de control de sesión en el cliente.
\end{itemize}
