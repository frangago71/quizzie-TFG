\section{Componentes clave e implementación del sistema}\label{sec:componentes_clave}

En esta sección se exponen los aspectos más representativos del núcleo de \textit{Quizzie}, analizando las decisiones de diseño y patrones de \textit{software} adoptados para dar respuesta a los requisitos funcionales más complejos: la comunicación bidireccional, la gestión del ciclo de vida de las salas y la seguridad del estado en el \textit{frontend}.

\subsection{Comunicación en tiempo real mediante \textit{WebSockets}}\label{subsec:impl_websockets}

La interactividad en vivo entre el profesor y los alumnos requiere una arquitectura de baja latencia capaz de difundir eventos de forma simultánea a múltiples clientes mediante el protocolo WebSocket~\cite{websocket_protocol}.

\subsubsection{Gestor de conexiones en el \textit{backend} (\texttt{ConnectionManager})}

En la ruta \texttt{backend/routers/stage.py}, el gestor de conexiones implementa una adaptación concurrente del patrón de diseño \textit{Observer}~\cite{gamma1994design} combinada con una arquitectura de publicación-suscripción (\textit{Pub-Sub})~\cite{eugster2003pubsub}, permitiendo registrar, desacoplar y administrar dinámicamente el ciclo de vida de las instancias activas de \texttt{WebSocket} asociadas a cada sala mediante su identificador único (\texttt{room\_id}).

\vspace{0.1cm}

\begin{lstlisting}[style=sourcecode, captionpos=b, caption={Gestor de conexiones en el \textit{backend}.}, label={lst:gestor_conexiones_backend}]
class ConnectionManager:
    def __init__(self):
        self.active_connections: Dict[int, List[WebSocket]] = {}

    async def connect(self, websocket: WebSocket, room_id: int):
        await websocket.accept()
        if room_id not in self.active_connections:
            self.active_connections[room_id] = []
        self.active_connections[room_id].append(websocket)

    def disconnect(self, websocket: WebSocket, room_id: int):
        if room_id in self.active_connections:
            if websocket in self.active_connections[room_id]:
                self.active_connections[room_id].remove(websocket)

    async def broadcast_to_room(self, room_id: int, message: dict):
        if room_id in self.active_connections:
            for connection in self.active_connections[room_id]:
                try:
                    await connection.send_json(message)
                except Exception:
                    self.active_connections[room_id].remove(connection)
\end{lstlisting}

Esta estructura permite emitir mensajes masivos en formato JSON mediante el método \texttt{broadcast\_to\_room}. Asimismo, incluye un mecanismo de tolerancia a fallos mediante un bloque \texttt{try-except} que elimina automáticamente las conexiones diferidas o corruptas sin interrumpir la emisión hacia el resto de los participantes.

Asimismo, la función de retorno del \textit{hook} \texttt{useEffect} (\textit{cleanup function}) garantiza el cierre formal del socket al desmontar el componente, previniendo fugas de memoria y conexiones huérfanas en el cliente.

\subsection{Gestión de sala, estado, tiempo y aleatoriedad}\label{subsec:impl_state_time}

El correcto funcionamiento de las sesiones depende de mantener la sala sincronizada y lista para todos los usuarios. Para lograrlo, el servidor asume el control centralizado de los eventos y las decisiones críticas, gestionando el avance del estado de la sala y evitando depender del estado o el reloj individual de cada cliente.

\subsubsection{Cálculo determinista del tiempo restante en UTC}
En \texttt{backend/routers/stage.py}, la medición del tiempo no depende del reloj del cliente, sino de la diferencia estricta de marcas temporales en UTC.

\begin{lstlisting}[style=sourcecode, language=Python, captionpos=b, caption={Cálculo del tiempo restante sincronizado en el \textit{backend}.}, label={lst:calculo_tiempo_restante}]
def get_calculated_time_left(room: Room) -> int:
    if room.is_paused:
        return room.remaining_time_at_pause
    if not room.timer_started_at:
        return room.remaining_time_at_pause

    now = get_utc_now()
    started_at = room.timer_started_at
    if started_at.tzinfo is None:
        from datetime import timezone as tz
        started_at = started_at.replace(tzinfo=tz.utc)

    elapsed = (now - started_at).total_seconds()
    calculated_time = room.remaining_time_at_pause - int(elapsed)
    return max(0, min(room.answer_time, calculated_time))
\end{lstlisting}

Al restar el instante actual (\texttt{get\_utc\_now()}) del momento de inicio (\texttt{timer\_started\_at}), el sistema inmuniza la cuenta atrás frente a retrasos de red o pausas de ejecución en el cliente.

\subsubsection{Pausa automática por desconexión del profesor}
Para mitigar imprevistos técnicos durante una sesión presencial, el servidor detecta si la conexión WebSocket del docente cae inesperadamente. En la ruta \texttt{backend/routers/stage.py}, se implementa una rutina de contingencia encargada de preservar la integridad temporal de la sala activa.

\begin{lstlisting}[style=sourcecode, language=Python, captionpos=b, caption={Rutina de pausa automática ante la desconexión del docente.}, label={lst:pausa_automatica_docente}]
async def handle_teacher_disconnect(room_id: int, db: Session):
    room = db.query(Room).filter(Room.id == room_id).first()
    if not room or room.is_paused or room.status != RoomStatus.IN_PROGRESS:
        return

    room.is_paused = True
    room.remaining_time_at_pause = get_calculated_time_left(room)
    db.commit()

    await manager.broadcast_to_room(
        room_id,
        {
            "type": "timer_update",
            "time_left": room.remaining_time_at_pause,
            "is_paused": True,
        },
    )
\end{lstlisting}

La función congela la partida almacenando el tiempo restante exacto en \texttt{remaining\_time\_at\_pause} mediante \texttt{get\_calculated\_time\_left} y notifica inmediatamente a todos los estudiantes, pausando la interfaz hasta la reconexión del profesor.

\subsubsection{Barajado determinista de opciones}
Para mitigar que los estudiantes puedan copiar visualmente la alternativa seleccionada en la pantalla de un compañero contiguo durante sesiones presenciales, el \textit{backend} altera la disposición de las opciones de respuesta. No obstante, delegar esta tarea en generadores de números pseudoaleatorios convencionales (como el módulo estándar \texttt{random} de Python) introduce dos problemas críticos: la pérdida de determinismo ante caídas de conexión y bloqueos en el análisis estático de código.

Herramientas de aseguramiento de calidad como SonarQube restringen el uso de generadores pseudoaleatorios estándar en flujos de datos sensibles, catalogándolos como debilidades de seguridad si no garantizan entropía criptográfica o cuando su estado mutable global puede generar condiciones de carrera entre hilos de FastAPI. Para cumplir con el \textit{Quality Gate} y preservar una arquitectura estrictamente sin estado (\textit{stateless}), se implementó en el mismo módulo del enrutador (\texttt{backend/routers/stage.py}) un algoritmo de barajado determinista basado en dispersión criptográfica:

\begin{lstlisting}[style=sourcecode, language=Python, captionpos=b, caption={Algoritmo de barajado determinista anti-copia.}, label={lst:barajado_anticopia}]
def deterministic_shuffle(items: List[dict], room_id: int, question_id: int) -> List[dict]:
    def sort_key(item):
        seed_str = f"{room_id}_{question_id}_{item['id']}"
        return hashlib.sha256(seed_str.encode("utf-8")).hexdigest()

    return sorted(items, key=sort_key)
\end{lstlisting}

El algoritmo ordena los elementos calculando al vuelo una clave derivada del algoritmo \textit{SHA-256}, resultante de concatenar el identificador de la sala (\texttt{room\_id}), la pregunta en curso (\texttt{question\_id}) y el identificador único de cada respuesta (\texttt{item['id']}). Esta solución aporta tres garantías técnicas fundamentales:

\begin{itemize}
  \item \textbf{Cumplimiento estricto de calidad (SonarQube):} Elimina el uso de funciones no seguras o pseudoaleatorias basadas en semillas globales mutables, superando las reglas de análisis estático sin requerir excepciones manuales en la tubería de CI/CD.
  \item \textbf{Idempotencia y tolerancia a fallos:} Al ser una función pura y reproducible, si un alumno pierde la conexión WebSocket o refresca el navegador en mitad de la cuenta atrás, el reenvío del evento recalcula exactamente la misma ordenación sin discrepancias con el estado previo.
  \item \textbf{Eficiencia y desacoplamiento de base de datos:} Evita persistir campos de ordenación efímeros en PostgreSQL o en memoria de sesión de FastAPI, reduciendo el volumen de operaciones de escritura por cada ronda de preguntas.
\end{itemize}

\subsubsection{Transición de preguntas y fase de verificación}
El \textit{endpoint} \texttt{PATCH /rooms/:room\_id/next-question} en el módulo \texttt{backend/routers/stage.py} coordina el avance secuencial del cuestionario o la transición a la fase final de la partida. Su diseño garantiza la persistencia del orden de preguntas en la sesión, la aplicación del barajado determinista y la sincronización en tiempo real vía WebSocket.

\begin{lstlisting}[style=sourcecode, language=Python, captionpos=b, caption={Transición entre preguntas y paso a verificación.}, label={lst:transicion_preguntas_verificacion}]
@router.patch("/rooms/{room_id}/next-question")
async def next_question(room_id: int, db: Annotated[Session, Depends(get_session)]):
    # [...] Validacion de existencia de sala y comprobacion de estado LIVE

    q_ids = [int(x) for x in room.question_order.split(",") if x] if room.question_order else [
        q.id for q in db.exec(select(Question).where(Question.quiz_id == room.quiz_id).order_by(Question.id)).all()
    ]
    if not room.question_order:
        room.question_order = ",".join(map(str, q_ids))
        db.add(room)
        db.commit()

    next_index = room.current_question_index + 1

    if next_index <= len(q_ids):
        next_q = db.get(Question, q_ids[next_index - 1])
        room.current_question_index = next_index
        room.phase = RoomPhase.ANSWERING
        room.remaining_time_at_pause = room.answer_time
        room.timer_started_at = get_utc_now()
        room.is_paused = False
        db.commit()

        options_list = [{"id": opt.id, "text": opt.text} for opt in next_q.options]
        if room.shuffle_options:
            options_list = deterministic_shuffle(options_list, room.id, next_q.id)

        # [...] Construccion del payload de estado y emision via WebSocket (next_question)
        await manager.broadcast_to_room(room_id, {"type": "next_question", "data": data})
        return data
    else:
        room.status = RoomStatus.VERIFYING
        participants = db.exec(select(Participant).where(Participant.room_id == room_id)).all()
        for p in participants:
            p.verification_token = secrets.token_hex(8)
            db.add(p)

        db.commit()
        await manager.broadcast_to_room(
            room_id,
            {"type": "room_verifying", "data": {"status": "VERIFYING", "total_questions": len(q_ids)}},
        )
        return {"status": "VERIFYING"}
\end{lstlisting}

Si restan preguntas por responder, el controlador actualiza el índice y emite el evento correspondiente. Al agotar la batería de preguntas, la sala cambia al estado \texttt{VERIFYING} y genera tokens criptográficos efímeros mediante \texttt{secrets.token\_hex(8)}.

\subsubsection{Verificación presencial mediante código QR}
Una vez concluida la partida, la calificación debe ser validada por el profesor escaneando un código QR generado en el dispositivo del alumno. En el módulo \texttt{backend/routers/stage.py}, el \textit{endpoint} \texttt{POST /rooms/:room\_id/verify-participant} gestiona la recepción de la carga útil del código QR para auditar y validar la calificación.

\newpage 

\begin{lstlisting}[style=sourcecode, language=Python, captionpos=b, caption={Validación del token y consolidación de calificación.}, label={lst:verificacion_participante_qr}]
@router.post("/rooms/{room_id}/verify-participant")
async def verify_participant(
    room_id: int, req: VerificationRequest, db: Annotated[Session, Depends(get_session)]
):
    statement = (
        select(Participant)
        .join(Student)
        .where(Student.name == req.nickname, Participant.room_id == room_id)
    )
    participant = db.exec(statement).first()

    # [...] Comprobacion de existencia, no verificacion previa y token efimero
    if not participant:
        raise HTTPException(status_code=404, detail=PARTICIPANT_NOT_FOUND)
    if participant.verification_token != req.token:
        raise HTTPException(status_code=400, detail="Token de verificacion invalido")
    if participant.is_verified:
        raise HTTPException(status_code=409, detail="Resultado ya verificado")

    actual_score = sum(a.points_earned for a in participant.answers)
    if participant.score != actual_score:
        participant.score = actual_score

    participant.is_verified = True
    participant.verified_at = get_utc_now()
    db.add(participant)
    db.commit()

    # [...] Notificacion en tiempo real via WebSocket de la verificacion
    await manager.broadcast_to_room(
        room_id,
        {
            "type": "participant_verified",
            "data": {"nickname": req.nickname, "participant_id": participant.id},
        },
    )
    return {"status": "success", "nickname": req.nickname}
\end{lstlisting}

El controlador valida el token efímero (\texttt{req.token}), recalcula la puntuación final sumando los puntos auditados, marca al participante como verificado y notifica la confirmación en tiempo real.

\subsubsection{Autenticación y protección de endpoints con JWT}
En \texttt{backend/auth.py}, se implementa un mecanismo de inyección de dependencias para autenticar las peticiones de los docentes mediante cabeceras HTTP.

\begin{lstlisting}[style=sourcecode, language=Python, captionpos=b, caption={Extracción y verificación criptográfica de cabeceras JWT.}, label={lst:autenticacion_jwt_backend}]
security = HTTPBearer()

def get_current_teacher_id(
    credentials: Annotated[HTTPAuthorizationCredentials, Depends(security)],
) -> int:
    token = credentials.credentials
    try:
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
        raw_sub = payload.get("sub")
        if raw_sub is None:
            raise HTTPException(status_code=401, detail="Token sin campo 'sub'")
        return int(raw_sub)

    except jwt.ExpiredSignatureError:
        raise HTTPException(status_code=401, detail="El token ha expirado")
    except jwt.PyJWTError:
        raise HTTPException(status_code=401, detail="Token invalido. Inicia sesion de nuevo.")
    except Exception:
        raise HTTPException(status_code=401, detail="No autorizado")
\end{lstlisting}

Esta función intercepta el \textit{Bearer token} emitido en las peticiones HTTP, descifra la firma criptográfica del estándar JSON Web Token~\cite{ietf_jwt_rfc7519} utilizando la clave secreta del servidor (\texttt{SECRET\_KEY}) y verifica su validez temporal antes de permitir el acceso a los controladores protegidos.

\subsection{Organización del plan de pruebas y matriz de trazabilidad}\label{subsec:organizacion_trazabilidad}

La \textit{suite} de pruebas se estructura modularmente y se alinea con la evolución temporal del proyecto, estableciendo una correspondencia unívoca entre la ingeniería de requisitos previa y los artefactos de verificación construidos:

\begin{itemize}
    \item \textbf{Trazabilidad con requisitos:}
    \begin{itemize}
        \item \textbf{Pruebas unitarias $\rightarrow$ Requisitos Funcionales (RF):} Garantizan que cada regla de negocio o cálculo atómico cumpla estrictamente con las especificaciones funcionales unitarias.
        \item \textbf{Pruebas de integración $\rightarrow$ Historias de Usuario (HU):} Verifican que la interacción coordinada entre capas satisfaga los criterios de aceptación desde la perspectiva del usuario.
        \item \textbf{Pruebas E2E $\rightarrow$ Casos de Uso (CU):} Validan el recorrido holístico del sistema simulando navegadores reales para cada caso de uso del sistema.
    \end{itemize}
    \item \textbf{Segmentación modular del sistema:} La batería de pruebas se divide según los dominios de la plataforma:
    \begin{itemize}
        \item En el \textit{backend}, las suites se organizan por áreas funcionales: \texttt{contenido} (cuestionarios y preguntas), \texttt{sesiones} (gestión de salas y sincronización en vivo) y \texttt{usuarios} (autenticación y perfiles).
        \item En el \textit{frontend}, las pruebas se delimitan en los cuatro módulos cliente principales: autenticación (\texttt{auth}), gestión (\texttt{management}), acceso a salas (\texttt{room-access}) y juego en vivo (\texttt{room-play}).
    \end{itemize}
    \item \textbf{Evolución por fases de desarrollo:} Las pruebas se estructuraron formalmente en tres bloques, correspondientes a cada una de las fases del proyecto (\hyperref[fase:mvp]{\textit{MVP}}, \hyperref[fase:core]{\textit{Core}} y \hyperref[fase:qa]{\textit{QA}}), facilitando la organización del trabajo y permitiendo abordar la verificación del sistema de manera progresiva y ordenada.
\end{itemize}

\subsection{Auditoría y umbrales de cobertura de código}\label{subsec:metricas_cobertura}

\section{Pruebas de carga y rendimiento}\label{sec:pruebas_rendimiento_carga}

Dada la exigencia de una comunicación bidireccional fluida en las sesiones en directo, se implementó un banco de pruebas de estrés mediante Locust. El escenario estándar evalúa el comportamiento del \textit{backend} sometido a una carga simultánea de \textbf{200 usuarios} virtuales concurrentes, incorporados progresivamente a una tasa de 15 usuarios por segundo durante 1 minuto continuo.

El reparto del volumen total de usuarios simulados se distribuye como se muestra a continuación, reflejando la composición realista de la audiencia y los roles del sistema:

\begin{enumerate}
    \item \textbf{\texttt{TeacherManagerUser}} (3\,\%, 6 usuarios): simula la navegación administrativa del profesor, la consulta del catálogo y la edición interactiva de cuestionarios.
    \item \textbf{\texttt{TeacherHostUser}} (2\,\%, 4 usuarios): modela a los profesores dirigiendo salas activas en tiempo real, ordenando el tránsito entre fases de preguntas y forzando el despliegue de las clasificaciones.
    \item \textbf{\texttt{StudentUser}} (95\,\%, 190 usuarios): representa al grueso del alumnado interactuando de forma concurrente, manteniendo conexiones persistentes mediante \textit{WebSockets}, emitiendo respuestas masivas al unísono y enviando señales periódicas de \textit{ping}.
\end{enumerate}

Para evaluar los tiempos de respuesta de forma rigurosa, se utiliza como métrica principal el \textbf{percentil 90 (P90)}. Este indicador asegura que al menos el 90\% de las peticiones analizadas se resuelven en un tiempo igual o inferior al límite establecido, garantizando una percepción de inmediatez para la inmensa mayoría de los usuarios concurrentes y evitando que los valores atípicos extremos distorsionen la evaluación del sistema.
